# 공통 프로젝트 맥락과 개발 협업

Claude Code·Codex가 프로젝트를 개발할 때 함께 읽는 기준이다. 안정적인 목표·결정·자료 위치만 이곳에 두고, 현재 작업과 다음 행동은 [handoff.md](handoff.md)에 기록한다. 아래 기획·디자인 요약은 2026-10-10 확인 기준이며 구현 상태는 실제 저장소와 대조한다.

## 목표와 범위

- 오브젠 연구소 AI모델팀 제안 졸업 프로젝트. 기간 2026-10-08~12-09, 팀 이용석·이규동.
- 제품 원문·이미지·제작 조건 → 자료 분석·핵심 메시지 → 구성안 → 사람 승인 → 문구·검증·HTML/CSS 출력 → 사람 최종 검토 → 1080×1080 PNG·ZIP.
- 톤업 선크림으로 전체 흐름을 확인한 뒤 추가 제품 A·B로 재사용성과 효율을 검증한다. 가상 자료 점검과 실제 제품 검증은 구분한다.
- 관리자 1계정 웹, 기업 환경에서 Docker 실행, 제작 시간·수정·품질·비용 분석을 포함한다. 회원가입·다중 사용자·결제·크롤링·웹 테마 편집은 범위 밖이다.
- 소프트웨어 개발은 Claude Code와 Codex를 교대로 사용한다. 서비스 생성 엔진은 기존 Claude Agent SDK 설계를 따른다. 개발 도구 교대만으로 서비스 엔진이나 평가 조건을 바꾸지 않는다.

## 유지할 설계와 이유

| 결정 | 이유·완료 기준 |
|---|---|
| 내용 JSON과 HTML/CSS 템플릿 분리 | 다른 제품에도 공통 규칙·템플릿을 재사용한다. |
| 구성안 승인과 최종 승인 분리 | 사람 확인 없이 다음 제작 단계나 승인 완료 상태로 넘어가지 않는다. |
| 원문 근거 연결 | 원문에 없는 효능·성분·수치·인증을 추가하거나 의미를 강화하지 않는다. |
| plan / copy / revise 작업 분리 | 서비스 실행 한 번이 사람 확인 대기 지점에서 끝난다. |
| 요청 카드만 수정·재출력 | 다른 카드의 데이터와 출력은 보존한다. |
| 성공 결과만 서비스에 반영 | 실패 시 이전 결과를 유지한다. 현재 출력 스크립트와 별개로 서버에서 보장해야 한다. |
| 자동 수정 최대 2회 | 반복 실패를 종료하고 원인을 보고한다. 입력·내용 누락은 임의로 채우지 않는다. |
| 같은 규칙·Skill·검증 스크립트 사용 | 실행 도구마다 제작 기준이 달라지지 않게 한다. |

상세 제작 절차는 [CLAUDE.md](../CLAUDE.md)가 기준이다. 개발 인수인계는 사람의 구성안·최종 승인을 대신하지 않는다.

## 자료를 읽는 순서와 범위

- 사용자의 최신 명시적 결정과 작업 범위를 확인하고, 이 문서·인수인계·실제 변경 파일을 대조한다.
- 기획·우선순위는 노션, 화면·배치는 Figma, 현재 동작·규격 값은 저장소 코드·설정·검증 결과에서 확인한다. 계획을 구현 완료로, 예시 숫자를 측정 결과로 취급하지 않는다.
- 자료가 충돌하면 수정 날짜와 근거를 확인하고 차이를 알린다. 근거 없이 범위·설계·평가 기준을 바꾸지 않는다.
- 매번 저장소·노션·Figma 전체를 다시 읽지 않는다. 아래에서 현재 작업에 필요한 자료만 연다. 외부 연결이 없으면 확인된 요약으로 가능한 작업을 진행하고, 재확인이 필요한 부분을 구분해 기록한다.

## 평가와 미결정

- 필수: 시간·수정 유형, 품질 지표, 토큰·비용, 대시보드, Skill v1/v2 비교, 직접 제작과 자동화 시간 비교. 반복 3회 일관성·블라인드 평가는 권장이다.
- 직접/자동 비교는 이용석 A 직접→B 자동, 이규동 A 자동→B 직접의 교차 순서. 같은 자료·카드 수·템플릿·검토 기준을 사용하고 대기·검토·수정 시간을 포함한다.
- 커버리지는 문자열 기반 근사 지표이며 의미 정확성은 사람 검토가 필요하다. 제작 실험의 모델·날짜·조건을 남기고 다른 조건의 결과를 섞어 해석하지 않는다.
- 관리자 웹 범위·Agent SDK 활용 인정·API 예산·배포 환경·평가 기준·공개 범위는 멘토 확인 사항이다. Node.js/React·TypeScript/SQLite/Docker는 설계 방향이며 실제 도입 상태와 세부 선택을 재확인한다.

## 개발과 교대 운영

1. 시작할 때 `git status --short --branch`, 최근 커밋과 관련 변경을 확인한다. 인수인계의 목표·완료 조건을 이어가되 실제 파일과 다른 기록은 바로잡는다. 다른 사람이 남긴 변경을 덮어쓰거나 되돌리지 않는다.
2. 작업을 작은 완료 단위로 나누고, 한 체크아웃에서는 한 도구만 수정·실행한다. 다음 도구는 기존 실행이 끝났는지 확인한다. 인수인계의 담당자 표기는 안내이며 잠금 장치는 아니다.
3. 승인된 작업 범위의 개발을 진행한다. 카드 제작 중의 제품 한정 쓰기 규칙과 소프트웨어 개발 범위를 구분한다. 입력 원본·실제 제작 로그를 개발 테스트로 덮어쓰지 않고 기존 임시 테스트 자료 방식을 사용한다. 비밀 값은 문서·답변·로그에 남기지 않는다.
4. 변경에 맞는 검증과 [CONTRIBUTING](../CONTRIBUTING.md)의 필수 확인을 수행한다. 통과한 검사는 변경이나 새 실패 근거 없이 반복하지 않는다. 문서만 변경했다면 링크·내용·차이 검토를 하고 미실행 검사를 명시한다.
5. 작은 작업의 완료·중단, 중요한 결정 직후에 `handoff.md`를 갱신한다. 한도 소진 직전까지 미루지 않는다. 큰 설계 결정은 관련 명세에 이유를 남기고 인수인계에서 연결한다.
6. 교대 전 파일을 저장하고 수정·실행을 종료한다. 진행 중인 서버·작업이 있으면 종류·상태·이어받는 방법을 기록한다. 다음 도구는 브랜치·미커밋 변경·검증 결과·다음 행동을 대조한 뒤 이어간다.
7. 인수인계는 최신 상태 중심으로 짧게 유지한다. 장문의 대화·전체 실행 출력을 복사하지 않는다. 기록은 Git으로 남기되 커밋·공유 여부는 사용자의 요청과 저장소 협업 규칙에 따른다. 교대를 위해 미완료 작업을 완료로 표시하거나 자동 push하지 않는다.

인수인계 갱신 항목: **확인 날짜·작성 도구 / 목표·완료 조건 / 현재 브랜치·기준 커밋·변경 파일 / 완료 / 미완료·실패·미검증 / 결정과 이유 / 검증 명령·결과 / 실행 중인 작업 / 다음 행동 1~3개**. 중간에는 진행 중으로, 종료 시에는 완료 또는 중단으로 정확히 표시한다. 새로 승인된 작업을 시작하면 이전 작업의 목표·완료 조건을 교체한다.
