# 공통 프로젝트 맥락과 개발 협업

Claude Code·Codex가 프로젝트를 개발할 때 함께 읽는 기준이다. 안정적인 목표·결정·자료 위치만 이곳에 두고, 현재 작업·최근 변경·다음 행동은 [handoff.md](handoff.md)에 기록한다. 아래 기획·디자인 요약은 2026-10-16 확인 기준이며 구현 상태는 실제 저장소와 대조한다.

## 용어

| 용어 | 뜻 |
|---|---|
| 대화 모드 | 팀원이 터미널의 Claude Code와 대화하며 카드를 만드는 **제작 방식**. 구성안·최종 승인을 대화로 받는다. (2026-10-10 이전 문서의 "개발 모드"와 같음) |
| 평가 모드 | 평가 실행기(`npm run eval`)가 `claude -p`로 작업 하나씩 실행하는 제작 방식. 질문하지 않고 끝내며 구성안 승인은 '평가'(`approved_by: eval`)로 기록. 10.10의 서비스 모드(관리자 웹 → Agent SDK)를 이름과 실행 주체만 바꿔 이어받음 |
| 결과 보기 웹 | 로컬에서 만든 결과·구성안·원문 근거·제작 기록·지표를 보여주는 정적 사이트. 생성·승인·로그인 기능이 없다. |
| 프로젝트 개발 | 이 저장소의 코드·웹·설정·문서를 고치는 작업. Claude Code·Codex가 교대로 하며 이 문서와 인수인계를 따른다. |

카드 제작 중의 쓰기·명령 제한(`cards.json`만 쓰기 등)은 대화·평가 모드에만 적용된다. 프로젝트 개발에서 `config/`·`templates/`·Skill처럼 제작 결과에 영향을 주는 파일을 바꾸면 [CLAUDE.md](../CLAUDE.md) '규칙 버전'에 따라 버전 변경 여부를 사람에게 묻는다.

## 목표와 범위

- 오브젠 연구소 AI모델팀 제안 졸업 프로젝트. 기간 2026-10-08~12-09, 팀 이용석·이규동.
- 제품 원문·이미지·제작 조건 → 자료 분석·핵심 메시지 → 구성안 → 사람 승인 → 문구·검증·HTML/CSS 출력 → 사람 최종 검토 → 1080×1080 PNG·ZIP.
- 톤업 선크림으로 전체 흐름을 확인한 뒤 추가 제품 A·B로 재사용성과 효율을 검증한다. 가상 자료 점검과 실제 제품 검증은 구분한다.
- **2026-10-16 결정**: 카드 제작은 팀원 PC의 로컬 Claude Code(대화 모드)로만 한다. 웹은 결과 보기 전용 정적 사이트(React·TypeScript, 배포 링크)이고, 검증을 통과한 결과를 `npm run export`(예정)로 내보내 보여준다. 분석은 실사용자 대신 평가용 입력 세트를 반복 실행한 결과로 하고, 평가 대시보드를 포함한다.
- 범위 밖: Agent SDK 서버 실행, 관리자 로그인·회원 기능, 서버 DB, Docker 배포, API 사용료 관리·토큰/비용 지표, 결제, 크롤링, 웹 테마 편집.
- 역할은 **기능·화면 단위**로 나눈다(10.16 개정). 이규동 = 웹 골격·V1 목록·V2 카드 결과·V2 제작 과정, 내보내기·평가 실행기·배포, 검증·출력 스크립트·템플릿, 제품 A·B, 평가 입력 6개, A6·A8. 이용석 = V2 구성안·근거·V3 평가 대시보드·V4 버전 비교, 핵심 정보 포함률·평가 집계·주의 표현 기준, `CLAUDE.md`·Skill, 톤업 선크림 제작, 평가 입력 6개, A5·A7. 두 사람의 기능은 **연결 규격 3개**(카드 구성 데이터 `docs/card-data-spec.md`, 웹 데이터 `docs/web-data-spec.md` 초안 이규동 10.21, 평가 결과·체크리스트 `docs/eval-spec.md` 초안 이용석 10.24)로만 이어진다. PR 리뷰어는 상대, 병합은 이규동. 자세한 내용은 노션 [개발 계획서](https://app.notion.com/p/3f56bcfa1f8a8188a029dfbab57ff761) 7장.
- 소프트웨어 개발은 Claude Code와 Codex를 교대로 사용한다. 개발 도구 교대만으로 제작 엔진이나 평가 조건을 바꾸지 않는다.

## 유지할 설계와 이유

| 결정 | 이유·완료 기준 |
|---|---|
| 내용 JSON과 HTML/CSS 템플릿 분리 | 다른 제품에도 공통 규칙·템플릿을 재사용한다. |
| 구성안 승인과 최종 승인 분리 | 사람 확인 없이 다음 제작 단계나 승인 완료 상태로 넘어가지 않는다. |
| 원문 근거 연결 | 원문에 없는 효능·성분·수치·인증을 추가하거나 의미를 강화하지 않는다. |
| plan / copy / revise 작업 분리 | 작업이 사람 확인 대기 지점에서 끝나고, 제작 기록에 작업 단위로 남는다. |
| 요청 카드만 수정·재출력 | 다른 카드의 데이터와 출력은 보존한다. |
| 검증 통과 결과만 웹에 공개 | 내보내기(예정)가 검증 오류·승인 전 제품을 제외한다. 웹은 결과 파일만 읽고 생성하지 않는다. |
| 자동 수정 최대 2회 | 반복 실패를 종료하고 원인을 보고한다. 입력·내용 누락은 임의로 채우지 않는다. |
| 같은 규칙·Skill·검증 스크립트 사용 | 실행 도구마다 제작 기준이 달라지지 않게 한다. |

상세 제작 절차는 [CLAUDE.md](../CLAUDE.md)가 기준이다. 개발 인수인계는 사람의 구성안·최종 승인을 대신하지 않는다.

## 자료를 읽는 순서와 범위

- 사용자의 최신 명시적 결정과 작업 범위를 확인하고, 이 문서·인수인계·실제 변경 파일을 대조한다.
- 기획·우선순위는 노션, 화면·배치는 Figma, 현재 동작·규격 값은 저장소 코드·설정·검증 결과에서 확인한다. 계획을 구현 완료로, 예시 숫자를 측정 결과로 취급하지 않는다.

## 평가와 미결정

- **2026-10-16 분석 방향**: 실사용자가 없으므로 사용 데이터 분석은 하지 않는다. **평가용 입력 세트 12개**(정상 8·경계 4: 입력 누락, 지시문, 과장된 원문, 긴 원문)와 입력별 **핵심 정보 체크리스트**를 만들고, **평가 실행기**(`npm run eval`, 예정)가 `claude -p`(비대화 Claude Code, 같은 `CLAUDE.md`·Skill 사용)로 반복 제작해 지표를 모은다. 평가 실행의 구성안 승인은 '평가' 자동 승인으로 기록해 사람 승인과 구분한다.
- 필수: A1 제작 기록(실제 자료 사례), A2 품질·처리 지표(1회 통과, 오류 코드, 자동 수정, 커버리지, 핵심 정보 포함률, 근거 연결률, [주의], 글자 수, 처리 시간), A3 평가 세트, A4 평가 대시보드, A5 규칙 v1/v2 비교(v2는 v1 평가의 오류 코드·핵심 정보 누락을 근거로 보완), A6 반복 일관성(4개 입력 × 3회), A7 안전성 테스트(경계 입력의 기대 동작). 권장: A8 규칙 구성요소 비교(규칙 일부를 뺀 비교판).
- 제외: 외부 평가자 블라인드 평가, 사용량 분석, 토큰·비용. 실행 수는 약 30~45회로 잡고, 사용량이 부족하면 A8부터 줄인다.
- 직접 제작과 자동화 시간 비교는 팀원 2명의 **사례**로만 남기고 일반화하지 않는다. 교차 순서(이용석 A 직접→B 자동, 이규동 A 자동→B 직접), 같은 자료·카드 수·템플릿·검토 기준을 사용하고 대기·검토·수정 시간을 포함한다.
- 커버리지는 문자열 기반 근사 지표이며 의미 정확성은 사람 검토가 필요하다. 제작 실험의 모델·날짜·조건을 남기고 다른 조건의 결과를 섞어 해석하지 않는다.
- 결과 보기 웹으로 '웹으로 구현' 피드백을 충족하는지, 웹 공개 범위, 실제 자료 제공, 평가 기준은 멘토 확인 사항이다. 웹은 React·TypeScript(Vite) 정적 사이트로 정했고 배포처는 미정이다.

## 개발 작업 규칙

**한 단계 완료** = 작업 → 검증 → 인수인계 갱신 → 이슈 브랜치에 커밋·push → PR → 노션 작업 트래커 갱신. `main` 병합은 저장소 관리자가 PR 검토 후 결정한다. 노션에 연결할 수 없는 도구는 인수인계의 다음 행동에 '노션 갱신 필요'를 남긴다. 이슈·브랜치 이름·커밋 메시지 형식은 [CONTRIBUTING](../CONTRIBUTING.md)을 따른다.


1. 시작할 때 `git status --short --branch`, 최근 커밋과 관련 변경을 확인한다. 인수인계의 목표·완료 조건을 이어가되 실제 파일과 다른 기록은 바로잡는다. 다른 사람이 남긴 변경을 덮어쓰거나 되돌리지 않는다.
2. 작업을 작은 완료 단위로 나누고, 한 체크아웃에서는 한 도구만 수정·실행한다. 다음 도구는 기존 실행이 끝났는지 확인한다. 인수인계의 담당자 표기는 안내이며 잠금 장치는 아니다.
3. 승인된 작업 범위의 개발을 진행한다. 카드 제작 중의 제품 한정 쓰기 규칙과 소프트웨어 개발 범위를 구분한다. 입력 원본·실제 제작 로그를 개발 테스트로 덮어쓰지 않고 기존 임시 테스트 자료 방식을 사용한다. 비밀 값은 문서·답변·로그에 남기지 않는다.
4. 변경에 맞는 검증과 [CONTRIBUTING](../CONTRIBUTING.md)의 필수 확인을 수행한다. 통과한 검사는 변경이나 새 실패 근거 없이 반복하지 않는다. 문서만 변경했다면 링크·내용·차이 검토를 하고 미실행 검사를 명시한다.
5. 작은 작업의 완료·중단, 중요한 결정 직후에 `handoff.md`를 갱신한다. 한도 소진 직전까지 미루지 않는다. 큰 설계 결정은 관련 명세에 이유를 남기고 인수인계에서 연결한다. 규칙·용어·파일 위치처럼 **다음 도구가 모르면 틀리게 작업할 변경**은 인수인계 '최근 변경'에 한 줄로 남긴다.
6. 교대 전 파일을 저장하고 수정·실행을 종료한다. 진행 중인 서버·작업이 있으면 종류·상태·이어받는 방법을 기록한다. 다음 도구는 브랜치·미커밋 변경·검증 결과·다음 행동을 대조한 뒤 이어간다.
7. 인수인계는 최신 상태 중심으로 짧게 유지한다. 장문의 대화·전체 실행 출력을 복사하지 않는다. '최근 변경'은 최근 10개만 두고 오래된 것은 Git 기록에 맡긴다. 교대를 위해 미완료 작업을 완료로 표시하지 않고, `main`에 직접 push하지 않는다.

인수인계 갱신 항목: **확인 날짜·작성 도구 / 이슈·PR / 목표·완료 조건 / 현재 브랜치·기준 커밋·변경 파일 / 완료 / 미완료·실패·미검증 / 결정과 이유 / 검증 명령·결과 / 실행 중인 작업 / 다음 행동 1~3개**, 그리고 해당하면 **최근 변경** 한 줄. 중간에는 진행 중으로, 종료 시에는 완료 또는 중단으로 정확히 표시한다. 새로 승인된 작업을 시작하면 이전 작업의 목표·완료 조건을 교체한다.
