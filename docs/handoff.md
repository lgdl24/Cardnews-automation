# 개발 인수인계

프로젝트 개발을 교대할 때 실제 파일·Git 상태와 함께 확인한다. 운영 규칙은 [project-context.md](project-context.md), 카드 제작 상태·승인은 해당 제품 데이터와 제작 로그가 기준이다.

## 현재 작업

- 확인일·작성 도구: 2026-10-10 · Codex.
- 상태: Claude Code ↔ Codex 교대 개발 문서 구성 완료. 후속 기능 개발은 아직 시작하지 않음.
- 사용자 요청: 두 도구가 같은 목표를 보고 이어서 개발할 수 있도록 현재 저장소에 준비.
- 완료 조건: 두 진입 지침이 같은 목표·인수인계를 연결하고, 기존 카드 제작·서비스 규칙의 적용 범위를 명확히 하며, 다음 도구가 확인된 상태부터 이어갈 수 있어야 함.
- 작업 브랜치: `docs/agent-handoff` (실제 브랜치는 시작할 때 재확인).
- 기준 커밋: `92ea3de` · v0.5. 이번 문서 변경은 미커밋이며 커밋·push·PR은 수행하지 않음.
- 변경 파일: `AGENTS.md`, `CLAUDE.md`, `README.md`, `CONTRIBUTING.md`, `docs/project-context.md`, `docs/handoff.md`.
- 실행 중인 개발 서버·API 작업: 이번 작업에서 시작한 것 없음. 교대 후 실제 프로세스 상태는 확인 필요.

## 완료한 내용과 결정

- 공통 목표·설계 이유·노션/Figma 링크·작업별 참고 경로를 저장소 내부 `project-context.md`에 정리.
- Codex 진입점 `AGENTS.md` 추가, Claude 진입점 `CLAUDE.md`에 요청 종류별 안내 추가. 공통 운영 규칙은 한 문서를 참조해 중복을 줄임.
- 코드·웹·문서 개발과 카드 제작의 “개발 모드”를 구분. 서비스 실행은 개발 인수인계를 읽거나 갱신하지 않도록 지정.
- 작은 작업 완료·중단마다 인수인계 갱신, 같은 체크아웃 단일 편집자, 실제 변경과 검증 결과 대조를 공통 운영 규칙으로 정함.
- 제작 규칙 본문·Skill·설정·실행 코드는 변경하지 않았으며 규칙 버전은 v1 유지. 후속 제작 기준 변경 시 기존 버전 결정 절차를 따름.

## 검증

- 문서의 저장소 내부 링크와 두 진입점의 공통 문서 연결 확인.
- `CLAUDE.md`의 기존 `## 실행 방식` 이하가 기준 커밋과 동일한지 확인.
- `git diff --check` 및 변경 파일 범위 확인.
- `npm test`, 출력 테스트, SDK/API 호출은 미실행. 이번 변경은 문서·지침 연결이며 실행 코드·의존성은 변경하지 않음.
- 두 도구를 새 세션으로 실행해 자동 로딩·실제 교대까지 수행한 종단 검증은 아직 안 함. 다음 세션에서 읽은 지침과 이어갈 목표를 확인할 것.

## 프로젝트 기준 상태 (2026-10-10 확인)

- v0.5: 입력 확인·데이터/근거/글자 수 검증·HTML/PNG 출력·제작 로그·지표·자동 테스트 소스가 있음. 가상 톤업 선크림 제작 기록까지 확인됨.
- 실제 제품 자료로 전체 제작 검증은 대기. 가상 결과와 Figma 예시 수치를 성과로 일반화하지 않음.
- 서비스 `plan/copy/revise` 지시문과 `docs/service-mode.md`는 준비됨. SDK 의존성·실행 PoC·관리자 웹·DB·Docker 구현은 아직 없음.
- 마지막 저장소 확인 당시 `node_modules/`와 제품 출력 폴더는 없었고, JavaScript21개 문법 검사는 통과. 이번 세션에서 전체 테스트나 렌더링을 실행한 결과로 해석하지 말 것.
- 노션·Figma는 앞선 읽기 작업에서 확인한 2026-10-10 상태를 요약함. 이번 문서 구성 중 원격 변경 여부를 다시 조회하지 않음.

## 남은 문제·미결정

- Agent SDK 옵션·규칙/Skill 로딩·권한 제한·토큰/비용 기록은 아직 실동작 미검증. 서비스 설계 문서의 예시를 검증된 구현으로 취급하지 않음.
- 웹 세부 스택·인증·배포·API 비용과 멘토 확인 사항은 [공통 맥락](project-context.md)의 원본 링크 참고.
- 승인된 다음 기능 작업은 아직 지정되지 않음. 아래 PoC는 기존 계획상 다음 단계이며 이번 문서 정리 요청에 포함된 실행 작업은 아님.

## 다음 행동

1. 실제 프로젝트 폴더에서 이 문서와 공통 맥락을 읽고, 현재 브랜치·변경 파일을 대조해 교대를 시작한다.
2. 다음 기능 개발을 요청받으면 목표·완료 조건을 갱신한다. 기존 계획상 다음 후보는 Agent SDK PoC: 규칙/Skill 로딩 → 구성안 생성·검증 → 승인 대기 종료 및 입력 누락 시 중단 확인.
3. PoC에 착수할 때 서비스 설계 초안과 SDK 공식 문서를 확인하고, 의존성·API 설정 및 검증 결과를 실제로 확인한 범위대로 기록한다.
